# Agent System Implementation Notes

This document tracks the implementation entry points for [agent-system-architecture.md](agent-system-architecture.md).

## PyTorch Model Bridge

The Rust contract lives in `crates/sinomo-pytorch`. It owns stable request and response structs, process invocation, status reporting, and a `LanguageModel` provider adapter. PyTorch and Transformers stay isolated in `crates/sinomo-pytorch/python/pytorch_bridge.py`.

The checked-in bridge supports:

- text requests;
- vision requests with an image path or base64 image payload;
- audio and duplex request modes in the stable schema;
- a probe mode for dependency diagnostics;
- a mock mode for local smoke tests and benchmark harness checks without downloading the 9B model.

MiniCPM-o remains the first configured backend (`--provider minicpm-o`), but the bridge is intentionally named around the implementation boundary: any local PyTorch/Transformers model that can satisfy the request schema can be hosted behind `sinomo-pytorch-bridge` or `sinomo-pytorch-server`. Product runtime configuration is cluster-scoped and stored in cluster KV at `/config/lm/runtime`; use `sinomo models runtime set` instead of environment variables for model paths, device choices, and token budgets. During feature testing, prefix commands with `sinomo --local` to force local file-backed settings even on a clustered node; model runtime settings then live at `$SINOMO_DATA_DIR/configs/lm/runtime.json` as a shared config document.

The local model path follows the MiniCPM-o 4.5 PyTorch reference path. Current upstream docs recommend a Linux NVIDIA GPU with more than 28 GB VRAM for the full PyTorch demo. CPU mode is useful for dependency and wiring checks, but it is not expected to be fast enough for interactive full-duplex operation.

MiniCPM-o 4.5 currently depends on trusted remote model code that uses the Transformers 4.53 cache API. Use `transformers==4.53.3`; newer 4.x builds can load the checkpoint but fail at generation with `DynamicCache.seen_tokens` compatibility errors, and Transformers 5.x fails earlier in model loading. The Windows CUDA smoke also required `minicpmo`, `onnx`, `onnxruntime`, `hyperpyyaml`, and `diffusers` in addition to the base `torch`, `PIL`, and `accelerate` dependencies.

Local probe status from this implementation pass:

- an isolated Python 3.11 venv at `/tmp/sinomo-pytorch-venv` can import `torch`, `transformers`, `PIL`, and `accelerate`;
- `sinomo-pytorch-bridge --python /tmp/sinomo-pytorch-venv/bin/python` reports MiniCPM dependencies are importable;
- `torch.cuda.is_available()` is false on the local host, so the full 9B PyTorch model was not loaded here.
- a Windows node with an RTX 3090 was able to load `openbmb/MiniCPM-o-4_5` through the long-running managed PyTorch server with CUDA after pinning `transformers==4.53.3`; text and vision smoke requests completed through the local loopback runtime.

The PyTorch HTTP server is a private implementation detail of the Sinomo node that spawned it. The Rust supervisor binds it to loopback only, adds a per-process bearer token, writes stdout and stderr logs under `.sinomo/logs/pytorch`, observes readiness through `/health`, and restarts it when the process exits or stops answering. It must not be exposed on a LAN or used as a cross-node model endpoint.

Cluster model traffic must go through `sinomo-network`. A configured `pytorch_bridge.endpoint` is accepted only when it is a loopback endpoint for the same node. Clear older LAN endpoints with:

```sh
sinomo models runtime set --pytorch-endpoint ""
```

For a local-only test override, use:

```sh
sinomo --local models runtime set --pytorch-endpoint ""
```

The loop asks the model for a JSON decision with user-visible text, optional tool calls, optional background handoff, and the next interaction state. Quiet async updates can be consumed without calling the model.

`Agent` is the first coding-agent style loop for deliberation and self-evolution work. It normalizes provider calls through `LanguageModelRequest`, keeps both a model-visible transcript and provider-neutral typed `AgentItem` evidence, executes requested tools through a registry/orchestrator boundary, returns tool results as follow-up user messages, and emits `agent.loop.*` events. Each completed run also carries `AgentRunModelMetrics`, a compact provider-neutral summary of output format, parsed model-turn count, total sampled model-response count, model-response parse failures, strict-JSON decision turns, text-fallback turns, provider-native tool-call turns and call count, vendor-fallback tool-call turns and call count, repair attempts, model-visible repair-request bytes, provider-reported token usage, provider-reported repair-response token usage, and final decision source so callers do not need to reconstruct provider behavior from traces. `AgentToolPairIntegrity` derives tool-call/tool-result balance from the shared runtime step/call slot in `AgentItem` records, so benchmarks and candidate summaries do not need ad hoc orphan detection. Each `agent.loop.model.completed` event also carries the per-step `decision_source`, so live traces can distinguish strict JSON, text fallback, provider-native tool calls, and vendor-fallback tool calls before the run completes. By default, agent steps, per-step tool calls, model repair attempts, model output tokens, prompt-reference expansion, context size, and compaction are not hard-capped. Runtime layers can tighten those values when a concrete model or session configuration provides real limits; model-window inference and provider protocol system hints belong to `sinomo-lm` provider implementations, and `AgentContextBudget::for_loaded_model` converts loaded model metadata into an optional byte budget plus ratio-based compaction threshold.

The near-term coding-specific control plan is tracked in [plans/coding-agent-improvement-plan.md](plans/coding-agent-improvement-plan.md). That work should stay layered above the generic `Agent` loop so TUI chat, background agents, and non-coding workflows can keep using the same runtime surface.

`AgentDefinition` is the agent package artifact. It carries schema version, package version, provenance, prompt, declared tools, tool-surface projection hints, skill references, context strategy, compaction strategy, provider preferences, runtime limits, and output format in one serializable definition. Built-in definitions mark package provenance as `built-in`; stored/custom definitions default to `local`; module-projected definitions receive `module` provenance from the module registration id and version during catalog merge; imported package JSON is stored with `imported` provenance plus the source path. Package validation rejects malformed ids, package versions, tool names, duplicate tool names, tool-surface entries, skill refs, context provider refs, blank model preferences, invalid temperatures, conflicting legacy/model-policy limits, zero step/tool-call limits, and unknown context or compaction strategies before a definition enters the catalog or file store. `FileAgentDefinitionStore` round-trips these packages under `$SINOMO_DATA_DIR/agents/*.json`, and `AgentCatalog` still treats built-ins, stored definitions, imported packages, and module exports as one package catalog rather than a separate runtime-profile layer. `AgentConfig::with_agent_definition` treats runtime caps equal to the previous package as package-derived, so switching to an unbounded package clears stale caps while caller-provided explicit caps survive package swaps. That cap-source distinction also survives JSON persistence: package-derived caps do not serialize explicit override markers, while caller-provided caps do. `sinomo agent inspect [agent-id] [--json]` exposes an inspection path for package prompt, visible toolsets, skills, context strategy, compaction strategy, effective provider preferences, raw model policy, runtime limits, tools, and provenance. Text inspection renders absent step, tool-call, and repair-attempt caps as `unbounded`, matching the continuous-agent default; JSON inspection preserves the raw optional `runtime_limits` fields. `sinomo agent validate [agent-id|--file <path>] [--json]`, `sinomo agent export [agent-id] [--output <path>]`, and `sinomo agent import <path> [--json]` provide direct package-artifact validation and exchange without adding a runtime-profile layer.

The current architecture surface now has a session/turn split: `Agent::start_turn`, `continue_turn`, `steer`, `follow_up`, `compact`, and `abort` operate on `AgentSession`, while `Agent::run` remains the compatibility helper for one-shot runs. `AgentSession` keeps a model-facing projection transcript plus an append-only raw transcript so compaction does not destroy source history. `start_turn` projects typed session transcript into model-visible history, and queued steering/follow-up messages are consumed into the next turn as an `agent_queued_turn_context` user message. Every model step assembles a `TurnContext` and records a `ContextAssemblyReport` with included sources, omitted context, and byte-budget estimates. The model request includes a structured `turn_context` message with runtime facts, workspace facts, current session projection/working state, async updates, workspace instruction files such as `AGENTS.md` as authored by the user, and prompt-reference expansions for `@file` and `@directory` mentions when `AgentConfig::workspace_root` is configured. Workspace instruction files, prompt-reference files, context attachment payloads, and async task updates are each bounded by default to 64 KiB, with projected context attachment payload JSON and async-update JSON fitting within their configured model-visible byte budgets after metadata and JSON escaping. Prompt-reference directories are bounded to 200 entries, and explicit `AgentConfig` overrides can tighten, loosen, or disable those caps for sessions that own a different context budget. Package prompts stay role-oriented: the runtime now keeps output contracts and provider-native tool hints in `sinomo-lm` system-instruction rendering, while tool schemas live in `LanguageModelRequest.tools`; plain-process provider prompts render those request tools from `sinomo-lm` instead of copying tool behavior into the package prompt. `ContextBudgetEstimate` now includes budget lanes for fixed prompt, current work, recent tail, retrieved memories, old summaries, prompt references, generic context attachments, async updates, and tool-surface availability so future memory retrieval and projection pruning can be managed deliberately. `sinomo-lm` exposes provider-neutral `LanguageModelStreamEvent` values for text deltas, reasoning summaries, tool-call start/delta/completion, usage, finish, error, and abort events. `Agent` converts those into `AgentModelEvent` records, while providers that only return a completed response fall back to one completed-response delta.

Self-evolution is an R2 caller of the generic agent loop rather than a built-in agent mode. It passes `AgentLoopInput::context_attachments` that summarize an evolution job, mutation packet, candidate bundle, or prior evidence as generic typed JSON. `ContextAssembler` records these as model-visible `TurnContext::context_attachments`, includes their projected byte cost in `ContextBudgetEstimate`, and renders the bounded projection into the model-facing `turn_context` message. The original attachments remain on `AgentLoopInput`; when attachments are present, `AgentRun::candidate_evidence_bundle` collects the final response plus patch snapshots and verification results from the full run input, giving the caller a provider-neutral evidence summary before any evolution-specific durable packaging is attached. Evolution candidate bundles persist the complete `agent-run.json`, line-oriented `agent-events.jsonl`, `coding-run-state.json` when coding-state evidence exists, separate `patch-snapshots.json` and `validation-records.json` review artifacts when present, and a compact `agent-summary.json`; the summary carries the serialized `AgentRunModelMetrics` and `AgentToolPairIntegrity` so candidate review can inspect provider path, parse failures, repairs, tool-call mode, token usage, final decision source, and orphan tool-call evidence without parsing the full run trace. Approval-time `candidate-summary.md` also renders the compact agent summary when present, so reviewers see the same stop reason, turn/tool counts, token counts, final decision source, and tool-pair integrity before opening the raw JSON artifacts.

`Agent` treats malformed deliberation-model output as recoverable. The loop records the unparseable response as `AgentItem::Error` plus `AgentModelEvent::Error`, counts it in `AgentRunModelMetrics::repair_attempt_count`, then sends a focused JSON repair message to the model. `AgentConfig::max_model_repair_attempts` is optional: when runtime configuration sets it, exhaustion fails with `AgentError::ModelResponse` after preserving the failed attempts in trace state; otherwise repair attempts are left unbounded for the session runtime to cancel or steer.

`AgentSessionStore` is the reloadable session-state boundary. `FileAgentSessionStore` stores a pretty JSON snapshot at `events/agent/sessions/<session>/snapshot.json`, appends session lifecycle records to `events/agent/sessions/<session>/events.jsonl`, appends raw typed items to `items.jsonl`, and appends session projections to `projections.jsonl`. `Agent::with_session_store` attaches it to the runtime; `start_turn`, `steer`, `follow_up`, `compact`, and `abort` update the snapshot and append session records, while `Agent::load_session` and `Agent::save_session` expose explicit reload/save hooks. The snapshot is the canonical resume projection; item and projection streams are the append-only audit trail; traces remain observability/evidence.

`AgentSessionControlPlane` is the local async task/session operation surface. It serializes active-turn state, task snapshots, task progress summaries, result refs, terminal statuses, and buffered events through `AgentSessionControlSnapshot`; snapshots can be restored for resume/inspect flows. `AgentSessionControlEventCursor`, `progress_since`, `terminal_result`, and `terminal_results` provide the inspect/resume surface expected by TUI, RPC, and evolution callers. `AgentSessionControlResult::persist_to_store` publishes control events, task-status changes, and control snapshots through the session store, and `FileAgentSessionStore::load_control_snapshot` plus `load_control_events` reload the durable snapshot and progress stream from `events.jsonl`. `AgentRuntimeService` exposes read-only object-RPC routes for persisted session inspect, progress, and terminal results (`/agent/session/inspect`, `/agent/session/progress`, `/agent/session/terminal-results`). `sinomo agent session inspect|progress|terminal-results` calls those daemon-hosted routes and can print either compact summaries or the exact typed JSON responses. `AgentRuntimeControlService` adds host-injected object-RPC routes for steer, follow-up, interrupt, and resume (`/agent/session/steer`, `/agent/session/follow-up`, `/agent/session/interrupt`, `/agent/session/resume`) through the `AgentRuntimeControlHost` trait; `AgentRuntimeControlRegistry` is the reusable host implementation for live `AgentSessionRuntime` handles, type-erased through `AgentRuntimeControlSession`. The matching `sinomo agent session steer|follow-up|interrupt|resume` commands call those control routes when a long-running host has registered them. Resume responses carry `runtime_attached` plus a typed `reattach` report: live hosts return `live_runtime_attached`, while a restarted or empty host returns either `persisted_metadata_only` with active-turn/task/event counts or `missing`, instead of failing the route outright. The runtime-backed TUI/app chat handler owns an `AgentRuntimeControlRegistry` and registers live session handles as runtimes are created, resumed, or swapped, so an embedding host can control those sessions without knowing the concrete model type. `AgentChat` exposes first-class GUI-facing `steer`, `follow_up`, `interrupt`, and `control_state` methods over that registry with plain status/state return structs, including the resume reattach state for GUI callers; the graphical app chat worker carries matching control commands/events so the running app process can route control requests to its active runtime, and the composed app chat UI can queue follow-ups with Enter during a stream or press Interrupt for the active turn. The default daemon `register_services` hook stays read-only, while `register_services_with_runtime_control` is available to a process that owns active runtime scheduling. The R1 daemon remains generic: it accepts service-registration hooks, and the shipped application CLI supplies `sinomo_agent::register_services` when starting the daemon, so the persisted inspect surface is daemon-hosted without making `sinomo-daemon` depend on R2. Daemon/process-level exposure and real in-flight task reattachment remain host responsibilities.

`AgentTraceStore` is the append-only trace-store boundary. `FileAgentTraceStore` writes JSONL records for run boundaries, context reports, provider-neutral model events, typed transcript items, tool outcomes, compactions, and emitted runtime events. `Agent` uses no-op session and trace stores by default, and callers opt into durable session state and traces independently.

`AgentStoragePaths` derives the Sinomo-owned agent subtree from `SinomoDataDir`: session snapshots, lifecycle records, raw item records, and projection records live under `events/agent/sessions/<session>/`, traces live under `events/agent/traces/<session>.jsonl`, and full tool evidence lives under `events/agent/evidence/<session>/...`. `FileAgentSessionStore::for_data_dir`, `FileAgentTraceStore::for_data_dir_session`, and `LocalWorkspaceAgentConfig::with_data_dir_evidence` wire those paths into the first local implementation. `sinomo-agent::register_storage_paths` registers `events/agent` as the R2 escape subtree used by the CLI storage-contract layout.

`AgentToolSurface` is the first session availability bundle, with `AgentPolicyBundle` retained only as a deprecated compatibility alias. `ToolAvailability` is the primary filter type, with `AgentToolPolicy` retained as a deprecated compatibility alias; `AgentToolPolicyDecision` is likewise a deprecated alias for `AgentToolAvailabilityDecision`. A surface can include or exclude tools by name and by declared `AgentToolCapability` values such as `ReadWorkspace`, `WriteWorkspace`, `ExecuteProcess`, `InspectVersionControl`, `AccessNetwork`, `PromptUser`, `Delegate`, `ObserveEnvironment`, `CallModel`, `CallModule`, `ManageBackgroundTask`, and `InspectClusterState`. This is not a human approval model: a tool that is visible in the session is available to the agent. Strictly forbidden resources should be absent from the registry and cut off by the sandbox or tool execution environment. The tool surface filters model-visible tool schemas before context assembly and keeps a runtime guard for hallucinated or stale hidden-tool calls. Hidden tools are recorded in the `ContextAssemblyReport` omitted-context list, and blocked hidden-tool calls return model-visible blocked tool results with `error = "tool_unavailable"` and `AgentToolEvidence.availability.allowed = false`. Persisted records still accept the old `policy_id` and `policy` field names as compatibility aliases.

Tool contracts and implementations now live under `crates/sinomo-agent/src/tools/`. The shared `AgentTool` trait, descriptors, outcomes, evidence, and dynamic `AgentToolRegistry` are separated from the loop. The local workspace built-ins live in `tools/local_workspace/`, with each tool in its own file (`read_file`, `list_files`, `search`, `apply_patch`, `changed_files`, `git_diff`, `run_command`, command-session tools, and `request_user_input`). `AgentToolRegistry` is an interior-mutable handle: callers can register a tool, replace an existing tool with the same name, remove a tool, clear the registry, or clone the registry handle for runtime extension and future MCP/plugin registration. `Agent::tool_registry`, `Agent::register_tool`, and `Agent::remove_tool` expose that dynamic surface without changing the main turn loop.

Progressive tool disclosure is implemented by orchestrator-owned `tool_search`, `tool_describe`, and `tool_call` bridge tools. These bridge tools are injected into the per-turn `AgentToolPlan`, can inspect planned-but-hidden descriptors, and route target `tool_call` execution through the same tool-surface availability and registry evidence path without making large module/plugin/MCP toolsets directly model-visible. `AgentToolPlan::readiness_issues` provides the first reusable preflight gate for visible tools that lack runtime executors; context assembly filters those tools out of the model-visible schema list and records `tool_readiness` omissions, while runtime calls still return a blocked `missing_executor` result if an invalid plan reaches execution. Every tool orchestration evidence record now preserves the registry generation and visible toolsets from the exact plan used to evaluate that call, including blocked missing-executor and stale-tool paths. `AgentModuleToolProjection` lets higher runtime layers provide module catalog registrations plus loader state; active module object-RPC routes are projected as hidden `module_rpc_*` descriptors, and attached runtime executors can override those descriptors by registering the same tool name.

Progressive skill disclosure follows the same pattern without adding a separate runtime-profile layer. `skill_search`, `skill_describe`, and `skill_activate` are injected as discovery bridge tools. They search and describe skills declared by the active `AgentDefinition` package plus module declarative `Skill` resources projected through `AgentModuleToolProjection`. Package skill ids are retained even when no module descriptor is available; module skill descriptors carry module id/version, path, targeting metadata, activation tags, capability requirements, and embedded skill text when the module declared it inline. Skill search/describe output carries an explicit `activation` contract with `mode = "host_runtime"` and `available = false`, so agents can distinguish descriptor disclosure from activation. `skill_activate` gives guessed activation attempts a first-class blocked result with the same host-runtime metadata; actual activation still requires a host-provided executor rather than a generic prompt-level permission switch.

Compaction is represented by typed `AgentCompactionSummary` items, `AgentSessionProjection`, `AgentWorkingState`, and `agent.compaction.completed` events. The first compactor is intentionally deterministic: it records source item ids, retained item ids, previous projection lineage, current user request, active objective, pending tool state, file/evidence facts, verification state, blockers, and open risks. Explicit `Agent::compact` rewrites only the in-memory/model-facing projection while preserving raw transcript history, then persists the projection when a session store is attached. Automatic budget compaction records the same projection shape and uses it for subsequent model turns, but it does not yet run an auxiliary summarizer or garbage-collect old evidence from durable storage.

Coding-state, large tool outputs, and replayed tool inputs are projected deliberately. The durable `AgentItem::CodingRunState` keeps the complete reducer state, while the model-visible `coding_run_state` transcript message is a bounded projection with recent validation attempts, recent risks, changed-file counts, and omitted counts. Model-visible `read_file` results cap the prompt-facing `content` field even when the durable tool output keeps the complete selected content. Replayed prior tool calls, provider-native tool-call items, assistant JSON decisions, and the `tool_results.call.input` field cap large string inputs while preserving the full durable `AgentToolCall`. One step's `tool_results` transcript message also has an aggregate model-visible budget: results that exceed it become summary-only entries, and the same projection is used for provider-native tool-output items. This keeps repeated validation, command, file-read, and large tool-input history from growing the next prompt while preserving the full evidence in traces and session items. The first stop policy is conservative: patch-relevant validation failures keep the loop going, narrow patches can finish only after passed validation or classified dependency/setup/environment-blocked validation, and network or permission blockers terminate as blocked evidence rather than as ready patches. Final coding stop messages include the attempt-level validation failure label, such as missing command, missing dependency, or network unavailable, so the operator-facing result does not flatten typed evidence into a generic environment-blocked status.

The OpenAI Responses implementation path currently lives in `sinomo-lm` through the Codex provider's Responses renderer and stream parser. The Codex parser emits `LanguageModelStreamEvent` records from Responses SSE blocks for text, reasoning, tool calls, usage, completion, and failure. The durable `sinomo-agent` transcript is provider-neutral so future Chat Completions-compatible local servers, Anthropic, Google, process-backed coding agents, and smaller interactive models can render from the same `TurnContext`.

The bundled local workspace registry is intentionally conservative: `read_file`, `list_files`, and `search` are available under the configured workspace root with bounded outputs and path-escape checks. `apply_patch` is the only standalone workspace source-editing tool: it accepts Sinomo `*** Begin Patch` freeform patches or structured JSON edit operations, applies add/update/delete/move/full-file-replacement changes directly inside the workspace root, and supports small structured edits through `replace_exact` and one-based inclusive `replace_range` entries. Exact replacements must match once, range edits preserve existing file style, and every structured change is preflighted before any file is mutated. The tool records changed files, preserves the submitted patch or JSON changes as evidence when an evidence directory is configured, and emits an `AgentItem::PatchSnapshot` for review/rollback context. It is blocked unless the caller explicitly enables file writes on `LocalWorkspaceAgentConfig`. `changed_files` and `git_diff` remain registered version-control helpers, but they are hidden from the default prompt surface and are reached through progressive tool disclosure when needed. `run_command` and command sessions are blocked unless shell commands are enabled. Formatting and test workflows are intentionally left to the model through `run_command` or to future session-specific extensions. `request_user_input` is visible in the model contract but blocked until an interactive runtime bridge is attached.

Tool results now carry a generic `AgentToolEvidence` envelope with the runtime availability decision, model-visible output size and truncation marker, durable artifact references, optional execution evidence, typed evidence records, and free-form metadata. Coding tools currently attach a `kind = "coding"` record whose payload is `AgentCodingToolEvidence` for patch refs, changed files, diff summaries, and verification state; non-coding tools can add their own record kinds without changing the envelope. Command results preserve stdout, stderr, exit status, duration, timeout state, truncation flags, and artifact refs, while the coding-state reducer adds attempt-level failure kinds for timeout, command setup, missing command, missing dependency, network unavailable, permission denied, environment blocked, and patch-relevant failures. Final coding stop text surfaces those failure kinds alongside the stop recommendation. Model-visible command diagnostics include duration, timeout, failure classification, bounded stdout/stderr/aggregate excerpts, and artifact-ref availability, while the prompt-facing raw stdout, stderr, and aggregate fields are capped separately and local or SIFS artifact URIs are omitted. Model-visible read-file output similarly caps the prompt-facing file content and marks it as `content_model_visible_truncated` when the durable result is larger. `LocalWorkspaceAgentConfig::with_evidence_dir` lets local tools preserve truncated read or command output behind a `full_output` artifact reference; `with_data_dir_evidence` uses the standard data-dir layout. `AgentStoragePaths::sifs_evidence_path_for_session` and `AgentToolArtifactRef::sifs` provide stable SIFS-compatible evidence refs. `LocalWorkspaceAgentConfig::with_sifs_evidence_mount` adds the concrete SIFS-backed write path: tools mirror full evidence bytes into the configured SIFS POSIX mount and return a `sifs://...` artifact ref when that mirror succeeds, falling back to the local evidence path otherwise.

Tool cancellation has a registry-level guard before any registered executor is invoked, so host-provided, module, plugin, MCP, and local tools all receive the same cancelled outcome when a turn has already been interrupted. Local non-command tools also check cancellation cooperatively during read, recursive list/search traversal, and `apply_patch` planning plus pre-mutation phases. `run_command`, `changed_files`, and `git_diff` use `AgentProcessManager` for active subprocess cancellation. The `sinomo-sandbox` container runner exposes a sandbox-owned cancellation token and removes the running container on cancellation; the sandbox service registers run operations by `sinomo-operation-id` and exposes `/sandbox/run/cancel` for `ObjectRpcCancelRequest` frames carrying `sinomo-cancels-operation-id`. Clustered daemon sandbox runs now receive the same token through `DaemonSandboxBackend`, the WASIX SIFS runner, and the native-module `is_cancelled` callback. Daemon-hosted native-dylib module object-RPC routes also register active `sinomo-operation-id` values and expose `/module/native-dylib/cancel`, so cancel-aware native modules can observe host cancellation through the existing ABI callback. The optional `module.benchmarks` native-dylib exports `/benchmarks/cancel-probe` as the first cancel-aware module fixture. Host-provided tools can register `AgentToolGateway` tasks with explicit start/wait/cancel handles; the adapter polls the agent cancellation token and invokes the gateway cancel handle for already-running work. Remote object-RPC tools can use `AgentRemoteObjectRpcTool`, which stamps a `sinomo-operation-id` on the run request and sends an `ObjectRpcCancelRequest` to the configured cancel route with `sinomo-cancels-operation-id` when the agent token is cancelled. Live-cluster proof for active sandbox interruption is available through the `cluster.agent.sandbox-active-cancel` test when a node has daemon sandbox execution prerequisites installed; active module-hosted cancellation is available through `cluster.agent.module-native-dylib-active-cancel` when the node has `module.benchmarks` installed.

`sinomo test run cluster.agent.runtime-routes --require-cluster` is the first live-cluster agent readiness probe. It uses the same `sinomo test` harness as DFS cluster probes, calls the running local daemon's read-only agent session inspect, progress, and terminal-results routes with a synthetic session id, and expects well-formed empty typed responses. This proves the current node hosts the agent session RPC surface without creating a model session or mutating cluster state.

`sinomo test run cluster.agent.runtime-persisted-session-routes --require-cluster` seeds a completed file-backed agent session in the configured Sinomo data dir, then reads it back through the daemon-hosted inspect, progress, and terminal-results routes, including cursor offset and last-event-id continuation plus terminal-result task filters. This proves the live daemon route package is not only registered, but also wired to the same durable session store used for restart/resume metadata.

`sinomo test run cluster.agent.module-native-dylib-cancel-route --require-cluster` probes the daemon-hosted native-dylib module cancel route with a synthetic operation id. It expects a typed inactive-operation response rather than an unknown route, proving the route is registered and reachable on the current cluster node before a cancel-aware module fixture starts active work.

`sinomo test run cluster.agent.module-native-dylib-active-cancel --require-cluster` starts the optional `module.benchmarks` `/benchmarks/cancel-probe` native-dylib route with `sinomo-operation-id`, sends `/module/native-dylib/cancel` with `sinomo-cancels-operation-id`, and requires the module response to report that it observed host cancellation. It skips when the benchmark module fixture is not active on the node.

`sinomo test run cluster.agent.sandbox-cancel-route --require-cluster` probes the daemon-hosted sandbox cancel route with a synthetic operation id. It expects a typed inactive-operation response rather than an unknown route, proving the route is registered and reachable on the current cluster node without starting sandbox work.

`sinomo test run cluster.agent.sandbox-active-cancel --require-cluster` creates a temporary daemon sandbox using the standard BusyBox toolchain id, starts `sh -c "sleep 30"` on the unary sandbox run route with `sinomo-operation-id`, sends `/sandbox/run/cancel` with `sinomo-cancels-operation-id`, and requires the running command to end through the cancelled path. It skips only when the cluster node lacks the required daemon sandbox runtime or BusyBox toolchain.

`sinomo test run evolution.self-dry-run` is the first self-evolution candidate readiness probe registered by a shipped native module. The generic CLI runtime accepts module-provided test-case hooks, and the evolution module owns this case. It runs the real `EvolutionOrchestrator::propose` dry-run path with a fake workspace and local verifier, then checks that the candidate bundle, mutation packet, scorecard, resource-usage record, diff, changed-file record, and command log were written without creating model artifacts.

`sinomo test run --tag <tag>` runs every registered test case with a matching tag through the same `sinomo test` harness and returns a suite summary. This gives readiness gates a stable grouped entry point without adding a separate runner: `sinomo test run --tag local-readiness` runs deterministic local cases such as `evolution.self-dry-run`, while `sinomo test run --tag agent-readiness --require-cluster` runs the registered agent readiness cases against the live cluster runtime. Skipped selected cases make the suite command fail, so missing live prerequisites cannot look like a passing readiness gate.

The GUI app now shares one `AgentRuntimeControlRegistry` between its chat worker and its app-started in-process daemon. When the app starts its own daemon, that daemon registers `sinomo_agent::register_services_with_runtime_control`, so the read-only session routes and steer/follow-up/interrupt/resume control routes are backed by the same active runtime handles the chat worker registers. External daemons still expose only their own hosted sessions; they cannot control an app process that attached to them over RPC.

Compaction quality evals live under the optional benchmark module, not under `sinomo-agent` unit tests. `modules/benchmark/sinomo-benchmarks/agent/run_compaction_eval.py --mode plan` emits the research plan for long-session resume, constraint retention, coding-after-compaction, and cluster-ops-after-compaction scenarios. `--mode fixture` validates the checked-in scenario definitions and scores a deterministic two-phase harness smoke, while `--mode run` calls `sinomo agent run` with the selected provider/model, feeds the generated compaction summary into the continuation probe, and writes marker-retention summaries under `benchmark-results/agent-compaction/`.

Examples:

```sh
sinomo agent run --prompt "Check cluster health later and tell me if anything is wrong."
sinomo agent run --provider codex --model gpt-5.2-codex --prompt "Summarize the current repo status."
sinomo --local agent run --provider deepseek --model deepseek-v4-flash --prompt "Summarize the current repo status."
```

`--local` is a global CLI flag. It bypasses cluster quorum/orphan guards for local-capable commands and reads or writes local config instead of cluster KV. This is useful for testing provider authentication, default model selection, runtime model settings, sandbox policy, and local-owned DFS data on a node that may already be part of a cluster. Shared local config documents live under `$SINOMO_DATA_DIR/configs/`; model/provider settings use `configs/lm/providers.json`, runtime model settings use `configs/lm/runtime.json`, provider credentials use `configs/lm/credentials/<provider>.json`, sandbox policy uses `configs/sandbox/policy.json`, DFS expose config uses `configs/dfs/expose.json`, rollout telemetry gates use `configs/rollout/telemetry/gates.json`, and self-evolution defaults use `configs/evolution/config.json`. Legacy files under `$SINOMO_DATA_DIR/config/`, `$SINOMO_DATA_DIR/providers/`, `$SINOMO_DATA_DIR/rollout/telemetry-gates.sobj`, and `$SINOMO_DATA_DIR/evolution/config.json` are read for one-time migration by their owner APIs. Registry trusted signer records remain registry trust state managed through `sinomo evolve trusted-signers`, not generic config settings.

## Benchmark Harnesses

`modules/benchmark/sinomo-benchmarks` is an application-level optional native-dylib module. It is outside default workspace builds and production runtime dependencies; development and self-evolution flows opt into it when they need benchmark catalog data or local research harness scripts.

The SWE-bench Verified runner records benchmark-host dependency evidence before execution. Its plan and summary JSON include command availability, Python importability, Docker reachability, agent-binary status, and blocking issues for the selected Sinomo, baseline, and official-evaluation paths, so host setup failures are separated from model outcomes.

Terminal-Bench 2.0 is represented through Harbor:

- current install smoke: `pip install harbor`;
- command smoke: `harbor run --help`;
- current dataset id from Harbor docs: `terminal-bench/terminal-bench-2`;
- adapter template: `modules/benchmark/sinomo-benchmarks/harbor/sinomo_harbor_agent.py`.

The Harbor adapter is an external agent. It runs the Sinomo agent loop on the host side with stored Codex credentials and uses Harbor's `environment.exec` only for bounded task-container commands. This keeps Sinomo tools and credentials out of the benchmark container.

MineStudio is represented through a vision-path smoke:

- current install smoke: `pip install minestudio`;
- import smoke: `import minestudio`;
- synthetic request-path smoke: `modules/benchmark/sinomo-benchmarks/minestudio/sinomo_minestudio_smoke.py`.

The smoke script has a local mock mode so it validates the vision request path without requiring the full MiniCPM-o model. Benchmark harnesses may still accept environment variables because they are local experiment launchers, but Sinomo runtime commands should read model runtime settings from cluster KV. The Docker runtime in `modules/benchmark/sinomo-benchmarks/minestudio/docker/compose.yml` builds a headless Xvfb/Mesa/OpenJDK 8 MineStudio container with an HTTP wrapper for `reset`/`observe`/`step` control from the host. The real action-loop runner is `modules/benchmark/sinomo-benchmarks/minestudio/minestudio_vision_action_loop.py`; it starts `minestudio.simulator.MinecraftSim`, reads rendered frames from `info["pov"]` or `obs["image"]`, asks MiniCPM-o for one action macro, applies the action with `env.step`, and repeats. It can also use the Docker wrapper by setting `SINOMO_MINESTUDIO_ENV_URL=http://127.0.0.1:18080`. `modules/benchmark/sinomo-benchmarks/minestudio/minestudio_live_duplex_loop.py` uses the same wrapper for a live-style duplex workflow: it samples chronological frame sequences, sends them to MiniCPM-o as streaming duplex requests, consumes incremental output chunks, and applies the recovered action back to MineStudio.

MCU-turbo is represented through a MineStudio-compatible task-config runner:

- clone the benchmark configs from `https://github.com/CraftJarvis/MCU` into `/tmp/mcu` or set `MCU_ROOT`;
- configure the product runtime with `sinomo models runtime set --pytorch-endpoint <server-or-proxy-url>`, then run `modules/benchmark/sinomo-benchmarks/mcu/sinomo_mcu_runner.py`;
- results are written under the gitignored `benchmark-results/` folder as per-task JSON, `summary.json`, and `case_studies.md`.

The MCU runner uses the benchmark YAML files from `MCU_benchmark/task_configs` and drives Sinomo's main-agent loop with Minecraft task text, init commands, a MineStudio-style observation summary, and an expected `send_game_action` macro. This is a lightweight integration benchmark for the Sinomo agent interface; full MCU scoring still requires running MineStudio simulator episodes and VLM video evaluation.

Agent compaction quality is represented as a live/model benchmark plan:

- plan smoke: `python3 modules/benchmark/sinomo-benchmarks/agent/run_compaction_eval.py --mode plan`;
- deterministic harness smoke: `python3 modules/benchmark/sinomo-benchmarks/agent/run_compaction_eval.py --mode fixture --summary-out benchmark-results/agent-compaction/fixture-summary.json`;
- live/model run: `python3 modules/benchmark/sinomo-benchmarks/agent/run_compaction_eval.py --mode run --provider codex --model gpt-5.2-codex`.

The checked-in scenarios exercise long-session resume, explicit constraint retention, coding continuation after compaction, and live-cluster operations after compaction. The harness scores exact marker retention in generated compaction summaries and in continuation probes that receive those summaries as the checkpoint input. Fixture mode reports scenario, phase, marker, and missing-marker counts without invoking a model. Live/model results are research/eval evidence; local readiness remains responsible only for deterministic projection and persistence invariants.

## Interactive Environment Contracts

Reusable interactive-environment contracts live in `sinomo-events`:

- `InteractiveStatePacket` describes environment kind, adapter, task, inventory, pose, nearby blocks/entities, health, hunger, and metadata;
- `InteractiveActionMacro` describes a bounded action in environment-neutral terms: verb, target, duration, stop condition, and parameters;
- `InteractiveTrajectoryStep` links state, action, and artifact references;
- event constructors emit `interactive.state.observed`, `interactive.action.requested`, and `interactive.trajectory.step.recorded`;
- `InteractiveArtifactStore` writes replay artifacts under the registered `events/interactive/trajectories` data-dir subtree.

The runtime storage layout registers interactive trajectory and screenshot subtrees through `sinomo-events::register_storage_paths`. These contracts are not Minecraft-specific and can be reused for other games, remote desktops, UI automation, and robotics-style environments.

MineStudio-specific code stays in `sinomo-benchmarks`:

- `minestudio/minestudio_action_bridge.py` maps generic action macros to a MineStudio/VPT-style action dictionary and can call `env.step` repeatedly;
- the same bridge records benchmark trajectory JSONL and optional screenshots;
- `mcu/sinomo_mcu_runner.py` uses the bridge to attach MineStudio action mappings and trajectory records to MCU case-study output.
- `minestudio/minestudio_vision_action_loop.py` runs a vision-only action loop against a real `MinecraftSim`: MiniCPM-o receives task text plus rendered `pov` frames, no structured game-state text, and the resulting action is mapped through the same bridge before calling `env.step`.
- `minestudio/minestudio_live_duplex_loop.py` emulates live full-duplex control without requiring wall-clock realtime execution: MineStudio frame sequences flow into MiniCPM-o while the model response is consumed as a stream, then the first recoverable action is stepped back into the environment. It also enables MineStudio's `RecordCallback` so high-frame-rate episode MP4s are saved next to the JSON and lower-rate observation PNG artifacts for visual review.

The Minecraft improvement workflow, benchmark failure detectors, evaluation criteria, and automation shape are tracked in [`minecraft-agent-improvement-workflow.md`](minecraft-agent-improvement-workflow.md).
